01 The five pillars of TS security

// every embed architecture answers each of these, in this order

Before any auth method or RLS rule, the architecture answers five questions in sequence. Skipping one shows up later as either a security gap or an operational mess that's expensive to undo. The rest of this document is essentially the menu of options under each pillar.

Pillar 01
Who am I?
Authentication. SAML, OIDC, or Trusted Auth.
Pillar 02
What can I do?
Roles & privileges. Assigned via groups, not users.
Pillar 03
What can I see?
Content access via sharing. Default share-nothing.
Pillar 04
Which data?
Row-level security, column masking, ABAC.
Pillar 05
Cloud platform?
Your warehouse may add its own controls on top.
i
The order matters
You can't answer "which data?" before you've answered "who am I?" The pillars are sequential — pillar 01 produces an identity that pillar 02 attaches privileges to, that pillar 03 grants content access to, that pillar 04 then filters by row. Get an upstream pillar wrong and downstream filtering is filtering the wrong thing.

02 The two big choices everything hangs off

// auth pattern · identity strategy

Most of the variation in TS embed architectures is two decisions made under different constraints. Once these are settled, the rest of the design is consequence.

CHOICE A · AUTH PATTERN

How does the user prove who they are?

EmbeddedSSO (TS authenticates directly via your IdP) vs Trusted Authentication (your app authenticates, then vouches to TS via a signed JWT). The 3 preconditions for EmbeddedSSO are real — if any is missing, Trusted Auth is the answer. Covered in §03 and §04.

CHOICE B · IDENTITY STRATEGY

One TS user per human, or one shared user?

Individual users (each real human has their own TS user record, created via auto_create) vs a single shared service account everyone mints tokens as. Individual users are right for almost everything. Covered in §14.

Two more choices follow once these two are made — which ABAC mechanism (formula variables via RLS, the current recommended path, or legacy filter_rules, still supported but on the legacy track as of 2026) and which multi-tenancy model (TS Orgs for strong isolation vs column filtering on a shared cluster for cost). Both are downstream of the first two.

03 The seven auth methods in the SDK, at a glance

// the full menu from the official docs · two are production-grade · the rest have narrower roles

The Visual Embed SDK's AuthType enum carries a handful of values, plus a few deprecated/hidden aliases (SSO and SAML, both mapping to the old 'SSO_SAML'). Seven are worth knowing — two of them, TrustedAuthTokenCookieless and EmbeddedSSO, are what real production embeds run on, and they're what the rest of this document goes deep on. The other five exist for narrower reasons: legacy compatibility, environments that can't iframe, or local development. Here is the complete picture before the deep dive.

Production-grade · the two you should default to

M1 · AuthType.TrustedAuthTokenCookieless
Recommended · default for embedTrusted Authentication, cookieless
Your backend mints a JWT using the secret_key; SDK uses it as a Bearer token. No cookies needed at the TS layer. Works across all browsers regardless of third-party cookie policy. Handles multi-tenant, multi-IdP, dynamic per-session ABAC. Requires a backend token service. The mint endpoint is auth/token/full for plain trusted auth and auth/token/custom when you need ABAC entitlements in the token (see §07). This is what §04–§09 cover in depth.
M2 · AuthType.EmbeddedSSO
Recommended · simpler when it fitsIdP redirect inside the iframe
TS authenticates the user directly via SAML or OIDC, inside the TS iframe. No backend token service. Requires single IdP, iframe-capable IdP, and CNAME on the TS instance. Per-session ABAC is limited (use group claims, pre-persisted values, or ACL tables — see §12). Internal apps with one corporate IdP are the natural fit.

Conditional · use when a specific constraint forces it

M3 · AuthType.TrustedAuthToken
Trusted Auth, cookie-based (legacy)
Same trusted-auth concept as M1 but TS session is cookie-backed rather than Bearer-token-based. Predates the cookieless variant. Per the official docs: use it when the IdP can't iframe, when users don't exist in your IdP, or when you have multiple IdPs without federation. Most teams should choose TrustedAuthTokenCookieless instead — third-party cookie blocking is widespread enough that the cookieless variant is the safer default.
M4 · AuthType.SAMLRedirect
Full-page SAML redirect
When the embedded content loads, the SDK redirects the entire host application to the IdP login page, not just the iframe. Used when the SAML IdP refuses to be iframed at all. Supports redirectPath for landing on a specific page after login, and inPopup: true for a popup-window flow instead of full redirect. UX cost: every embed load can route through a full redirect if the IdP session isn't already established.
M5 · AuthType.OIDCRedirect
Full-page OIDC redirect
The OIDC counterpart to M4. Same trade-off: full app redirect when the OpenID Provider can't be iframed. Supports the same redirectPath for post-login landing. Requires the TS cluster to be OIDC-configured against the provider. If you can get the IdP to allow iframes, prefer EmbeddedSSO; this is the fallback when you can't.

Dev / test only · never production

M6 · AuthType.None
Dev / pass-throughSDK does no auth
Pass-through mode. The SDK assumes the user is already authenticated to TS via some other path (an SSO flow that happened before embed load, a Basic auth login). The SDK doesn't add anything to the auth process. Per the docs, partitioned cookies must be enabled and users must have already gone through Basic auth or another flow. Not recommended for production; useful in development sandboxes where you want to minimize moving parts.
M7 · AuthType.Basic
Dev onlyUsername and password in init()
Frontend passes username and password straight to init(); SDK POSTs them to /tspublic/v1/session/login. Useful for local development, smoke tests, and CI. Never use in production — credentials in frontend code or config. Fails if MFA is enabled on the cluster. Requires CORS allowlisting. Treat as a debugging tool.

04 EmbeddedSSO vs Trusted Authentication

// the two patterns, side by side

These are the two production-grade authentication patterns for embedded TS. They differ in where authentication happens and how identity flows into TS. Everything else in the embed architecture follows from this single choice.

PATTERN A · AuthType.EmbeddedSSO

TS authenticates the user directly

The TS iframe redirects to your IdP, gets a SAML/OIDC assertion, creates the TS session. Your app doesn't broker auth at all. No token service, no secret_key, no JWT minting.

PATTERN B · AuthType.TrustedAuthTokenCookieless

Your app authenticates, then vouches to TS

Your app authenticates via your IdP. Your backend mints a TS JWT using the secret_key. SDK sends the JWT as Bearer. TS trusts the signature; never contacts the IdP directly.

The 3 hard preconditions for EmbeddedSSO

Each requirement maps to a real architectural constraint. Miss any one and the pattern doesn't work.

REQ 01Single IdP for everyone
The TS instance has one OIDC or SAML config. Every user authenticates through that one IdP. Multi-tenant SaaS where each customer has their own IdP breaks this immediately. Even one-off customer IdPs require per-Org OIDC (different setup, different feature).
REQ 02IdP supports iframe redirect flows
The IdP page must load inside an iframe. Many IdPs block this by default with X-Frame-Options: DENY or strict CSP frame-ancestors. Okta requires the "Enable iframe embedding" option; Azure AD requires whitelist config; some IdPs flatly refuse.
REQ 03CNAME configured on TS instance
TS needs a CNAME like analytics.yourapp.com matching your app domain — that's how the browser shares cookies between your app and TS without third-party cookie restrictions. Without a CNAME, Safari and Firefox strict-mode block the SSO flow entirely.
!
If any one of the three fails, EmbeddedSSO doesn't work
These aren't preferences — they're how the pattern works. Trusted Authentication has none of these requirements because it operates at the token layer, not the cookie/redirect layer.
i
The product feature for the cookie problem: partitioned cookies (CHIPS)
A CNAME is half the answer to third-party cookie blocking. The other half is the Enable partitioned cookies toggle under Develop > Customizations > Security settings (per-Org if Orgs are on). With it, ThoughtSpot sets its session cookie with the Partitioned attribute, so on browsers that support CHIPS the cookie persists for embedded content after login. This matters specifically for cookie-based auth and AuthType.None; it's the setting to check when an EmbeddedSSO or cookie-based embed works in Chrome but breaks in Safari/Firefox. Cookieless Trusted Auth sidesteps the whole issue.

i
The Q0 case is worth being explicit about
Apps with custom auth (their own username/password store, magic links, passkeys, WebAuthn, OAuth-but-not-OIDC) can absolutely embed TS. They just go straight to Trusted Auth: your backend authenticates the user however it already does, then calls TS's auth/token/custom with the secret_key and mints a JWT. No SAML or OIDC needed anywhere in the stack.
→
The single most useful question to ask up front
"Will different customers/tenants ever need different IdPs?" If yes, EmbeddedSSO is off the table from day one (unless federation is in place). For multi-tenant SaaS, this is almost always eventually yes. Trusted Auth is the safer architectural bet because it accommodates that future without rework.
!
Even when EmbeddedSSO is eligible, dynamic ABAC may push you back
If your filtering needs are per-session (tenant context, allowed customer lists, region overrides that change with shift or escalation), Trusted Auth's token mint hook is the cleanest way to inject those values. EmbeddedSSO requires group claims, pre-persisted variables, or an ACL table joined on ts_username (see §12) to handle ABAC, all of which are real but each trades simplicity for one of: granularity, freshness, or query cost.

06 The full Trusted Auth flow — Phase A & Phase B

// what happens every time a user logs in or a token refreshes

Trusted Auth has two phases. Phase A is your app authenticating the human against your IdP — this is the same thing your app would do regardless of TS. Phase B is your backend minting a TS JWT on that authenticated user's behalf. The two phases are stitched together inside your backend; TS sees only Phase B.

PHASE AThe user signs into your app

1
User opens your app Hits a route that requires authentication. No session cookie yet (or it's expired).
2
App redirects to your IdP Okta, Auth0, Entra, whichever. SAML or OIDC handshake begins.
3
IdP returns SAML/OIDC assertion User has proven identity. Your app validates the assertion against the IdP's public key.
4
App sets its own session cookie Signed cookie like ts_app_sess. Browser carries it on every subsequent request to your domain. This cookie lives entirely in your zone. TS never sees it.

PHASE BYour backend mints a TS JWT

5
Frontend asks your backend for a TS token The SDK's getAuthToken callback fires. It POSTs to /api/ts-token with the session cookie attached. Your backend reads the cookie, confirms the user is who they say they are. This is the cookie's only job.
6
Backend resolves ABAC for the user Queries your entitlements service or database for the user's attributes. Region, tenant, allowed customer IDs, role. Server-side data the user cannot influence.
7
Entitlements returns attributes Something like { region: "NA", tenant: "vantage_sales", allowed_customers: [...] }.
8
Backend POSTs to TS /auth/token/custom Includes the secret_key, username, auto_create: true, variable_values, validity_time_in_sec: 300, persist_option: REPLACE. This is where the trust boundary is crossed. TS validates the secret_key and trusts the request.
9
TS creates user if missing, stamps ABAC, mints JWT auto_create: true handles JIT provisioning in the same call — no separate API call needed. TS persists the variable values on the user record and returns a signed JWT.
10
Backend returns the JWT to frontend Frontend hands it to the SDK. SDK uses it as a Bearer token on subsequent embed requests. RLS rules using ts_var() filter every query the user makes.
// the trust boundary is crossed exactly once · the round trip is the TS API call
i
Token TTL and the auto-refresh that makes short TTLs painless
The default validity_time_in_sec is 300s (5 min). With autoLogin: true in the SDK init(), the SDK requests a fresh token before the current one expires — re-running steps 5 through 10 — so the user never sees a signed-out embed. That auto-refresh is what lets you run short TTLs without UX cost, and it's how entitlement changes propagate: change a user's region in your entitlements service, the next refresh picks it up. For tenant switches, force a refresh immediately rather than waiting for TTL. Note one nuance: ThoughtSpot's own guidance recommends a longer validity for cookieless (often 20–30 min), since the token is used as a bearer on every request; the tight-TTL stance in §07 is a deliberately stricter security posture, not the documented default. Cookie-based auth is the opposite — you can drop it under a minute, since the token is used once to establish a session.

07 POST /api/ts-token — the most critical endpoint

// it's YOUR endpoint, not a TS endpoint · six things happen inside it

The endpoint path can be anything — /api/ts-token, /auth/embed, /api/analytics/session. What matters is that you own it. ThoughtSpot does not provide it. Your backend implements it, your code runs in it, your security depends on doing it correctly. If any of the six jobs below are wrong, the whole security model is compromised.

The six jobs, in order

1
Authorize the incoming requestSecurity
Verify the request comes from a logged-in user of your app. Read your session cookie or auth header. Reject if not authenticated. This is what makes the endpoint not public. If you skip this, anyone on the internet can hit it and get TS tokens.
2
Identify the user from your trusted sessionSecurity
Extract user identity (user_id, tenant_id, email) from the authenticated session. NOT from request body, NOT from query params, NOT from client-controlled headers. The session cookie was set by your auth flow; it's trustworthy.
3
Resolve ABAC entitlements server-sideBusiness logic
Look up the user's attributes in your entitlements service or database: region, department, allowed customer IDs, role. Server-side data the user cannot influence. Returns something like { region: 'NA', tenant: 'vantage_sales', role: 'analyst' }.
4
Build the TS token payloadBusiness logic
Transform resolved entitlements into the TS API shape: variable_values, groups, username, auto_create, persist_option, validity_time_in_sec. Decide the TTL (see §06). Pick the username strategy (tenant-prefixed if shared cluster).
5
Call ThoughtSpot's Trusted Auth APIIntegration
POST to /api/rest/2.0/auth/token/custom with the payload AND the secret_key from your vault. TS validates the secret_key, persists the user record (creates if needed via auto_create), stamps the variable_values, returns a signed JWT.
6
Return the JWT & log to auditIntegration
Send the TS JWT back in the response body. The SDK's getAuthToken callback receives it. Also: log the call to your audit/SIEM with timestamp, user, tenant, entitlements stamped, success/failure.
i
Which endpoint: auth/token/full vs auth/token/custom
There are two v2 mint endpoints, and the choice matters. /api/rest/2.0/auth/token/full grants a full-access token and is what the majority of trusted-auth implementations use when they don't need token-stamped entitlements. /api/rest/2.0/auth/token/custom is the ABAC endpoint — it's the one that accepts variable_values (or legacy filter_rules / parameter_values) and is required for the per-session ABAC this document recommends. There's also auth/token/object for read-only access to a single object. One hard constraint: ThoughtSpot allows only one token-request workflow active at a time — either full or custom, not both in parallel — so a "full for some users, custom for others" design won't work. The code below uses custom because it stamps variable_values.

What it looks like in code

POST /api/ts-token · your backend handlersix jobs annotated
app.post('/api/ts-token', async (req, res) => {

  // ─── JOB 1: AUTHORIZE ──────────────────────────────────────
  const session = getSessionFromCookie(req);
  if (!session || session.expired) {
    return res.status(401).json({ error: 'unauthorized' });
  }

  // ─── JOB 2: IDENTIFY ───────────────────────────────────────
  // READ from trusted session, NEVER from req.body
  const user = session.user;       // { id, email, tenant_id }

  // ─── JOB 3: RESOLVE ENTITLEMENTS ───────────────────────────
  const abac = await entitlementsService.resolve(user.id);
  // → { region: 'NA', allowed_customers: ['acme'], role: 'analyst' }

  // ─── JOB 4: BUILD TS PAYLOAD ───────────────────────────────
  const tsPayload = {
    username: `${user.tenant_id}::${user.email}`,  // tenant-prefixed
    secret_key: vault.getSecret('ts_secret_key'),    // from vault
    auto_create: true,                  // default is already true
    display_name: user.name,
    email: user.email,
    groups: [                            // array of { identifier } objects
      { identifier: `tenant_${user.tenant_id}` },
      { identifier: `role_${abac.role}` }
    ],
    validity_time_in_sec: 300,                // see §06 on TTL choice
    persist_option: 'REPLACE',                 // MUST set explicitly — API default is APPEND
    variable_values: [
      { name: 'region_var', values: [abac.region] },
      { name: 'tenant_id_var', values: [user.tenant_id] },
      { name: 'customer_var', values: abac.allowed_customers }
    ]
  };

  // ─── JOB 5: CALL TS ────────────────────────────────────────
  const tsResponse = await fetch(
    'https://your-cluster.thoughtspot.cloud/api/rest/2.0/auth/token/custom',
    { method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify(tsPayload) }
  );
  if (!tsResponse.ok) {
    logger.error('TS token mint failed', { user: user.id });
    return res.status(502).json({ error: 'token_mint_failed' });
  }
  const { token } = await tsResponse.json();

  // ─── JOB 6: RETURN + AUDIT ─────────────────────────────────
  auditLog.write({
    event: 'ts_token_minted', user: user.id, tenant: user.tenant_id,
    abac, ttl: 300, ts_at: new Date()
  });
  res.json({ token });
});

What the frontend looks like (much simpler)

SDK init · your frontend~10 lines · no secret_key, no entitlements logic
import { init, AuthType } from "@thoughtspot/visual-embed-sdk";

init({
  thoughtSpotHost: "https://your-cluster.thoughtspot.cloud",

  autoLogin: true,                  // refresh the token before it expires

    const r = await fetch("/api/ts-token", { credentials: "include" });

  },

✓
The annotations are not optional
Each of the six annotated sections is a security boundary. Job 1 separates authenticated from public. Job 2 separates trusted from client-supplied. Job 3 separates server entitlements from anything the frontend might claim. Job 5 keeps the secret_key on the server. Skip any of these and you have an exploitable bug.

Implementation review checklist

Six questions to ask when reviewing a Trusted Auth implementation — your own or anyone else's. Walk through these with the handler code open.

#QuestionWhat "wrong" looks like
Q1Is the endpoint behind auth middleware?Hitting it without a session cookie returns anything but 401 → HIGH severity
Q2Where do ABAC values come from?Any value flowing from req.body, req.query, or client-set header into the mint → HIGH severity
Q3Where is the secret_key stored?In .env file, source, or hardcoded → HIGH severity. Must be vault.
Q4What is the token TTL?5–30 min is the sane band (TS recommends ~20–30 min for cookieless, sub-minute for cookie-based). With autoLogin on, the short end is painless. >1 hour is worth questioning; 24 hours is a finding (stale entitlements, slow offboarding, higher value if stolen).
Q5Are mints logged to audit?No write per mint with user/tenant/ABAC/ts → forensics impossible.
Q6Is rate limiting in place?An authenticated user shouldn't mint 1000 tokens/sec. Per-user rate limit catches misbehaving SDK retries.

08 The four common bugs in /api/ts-token implementations

// the four bugs that show up again and again in real implementation reviews
BUG 01

Reading entitlements from request body instead of session

Frontend sends POST /api/ts-token { region: "NA", tenant: "vantage_sales" }. Backend reads those and stamps them into the TS token mint. User opens dev tools, edits the request body to {"tenant": "competitor"}, gets a token scoped to the competitor's tenant.

✗ WRONG
const { tenant, region } = req.body;
// trusts client-supplied values
✓ RIGHT
const user = session.user;
const abac = await resolve(user.id);
// server-side lookup
BUG 02

secret_key in environment file checked into git

Developer hardcodes the TS secret_key in .env or worse, in source. Repo gets cloned, secret_key leaks, anyone can mint tokens as any user. Catastrophic — the secret_key is the master credential for the entire TS integration.

✗ WRONG
secret_key: "abc-123-def"
// hardcoded
✓ RIGHT
secret_key: vault.getSecret(...)
// AWS, HashiCorp, Azure

09 The four questions that always come up

// every team building this asks these four · here are the clean answers
Q1
If we're using Trusted Auth, what's the point of OIDC at all? Aren't they substitutes?

OIDC and Trusted Auth solve different problems at different layers. You need both — they aren't substitutes.

OIDC authenticates the human into your app. The user proves identity by signing into Okta or Entra. Your app gets back an ID token. Your app drops a session cookie. The user is now logged into your application.

Trusted Auth authenticates your backend into ThoughtSpot, on behalf of the user your app already knows. Your backend uses the secret_key to prove "I am the trusted backend, and the user I'm asking a JWT for is Alice, with these ABAC attributes." TS trusts your backend because of the shared secret — it doesn't need to know how Alice authenticated upstream.

✗ Mental model tripping you up

"ThoughtSpot needs to validate the OIDC session somehow"

If this were true, TS would need OIDC configured against your IdP, and you'd have two places to keep in sync. That's the model when you use EmbeddedSSO — not when you use TrustedAuthTokenCookieless.

✓ What's actually happening

"Your backend is the bridge between the two worlds"

Your backend reads the OIDC session cookie (its own cookie, nothing TS sees), confirms the user is logged in, looks up ABAC, then makes a separate call to TS using secret_key. The two auth systems are stitched together inside your backend.

✓
The takeaway
You do not need to enable OIDC on the TS cluster for embedded use. Your trusted-auth setup is complete and independent. Any OIDC integration on TS itself is for the standalone TS UI — useful for admin/analyst logins, not on the embed path.
Q2
What information does the session cookie contain? Why do we need it if nothing valuable is in it?

The session cookie never reaches ThoughtSpot. It's your own backend's cookie — your backend reads it to confirm who the user is before minting a token on their behalf.

Many flow diagrams label the request to /api/ts-token as "session cookie attached" which makes it look like TS is checking the cookie. It isn't. The cookie is the proof from the browser to your backend that the user is logged into your app. The secret_key is the proof from your backend to TS that this request is trusted. Two different credentials, two different trust relationships.

// two different credentials · two different trust boundaries
!
The thing to validate in code review
The cookie is what stops a bad actor from minting a token for someone else. If /api/ts-token doesn't strictly check the cookie before calling auth/token/custom, anyone who knows a valid email could request a JWT for that user. Treat /api/ts-token like any other authenticated endpoint.
Q3

No separate call. JIT user creation happens inside the same token-mint POST via auto_create: true.

Q4
We have two IdPs — Okta for customers and Entra for colleagues. How does this work with both?

Both IdPs converge on the same backend. ThoughtSpot never sees the difference — it only ever receives one kind of call from one trusted backend.

This is a structural benefit of the Trusted Auth pattern. IdP variation lives entirely in your app's authentication layer. Once a user is signed into your app — regardless of whether Okta or Entra got them there — your backend handles them identically from that point forward.

// IdP routing happens in your app · TS sees one shape

How your app routes between them: typical patterns are by subdomain (customers → portal.yourapp.com, employees → admin.yourapp.com), or by email domain on the login page, or by user selection. The routing logic is entirely in your app layer.

What changes in the ABAC payload: probably nothing structural — same variable names, just different values resolved from entitlements. Employees might get region_var = ["ALL"] with an admin override RLS rule; customers get their actual region. Your entitlements service decides what to stamp based on who the user is, not how they logged in.

✓
Why this beats configuring both IdPs against TS directly
The alternative — per-Org OIDC on the TS side — requires Orgs enabled, requires Support tickets to change, and disables IdP-driven group sync. The Trusted Auth pattern keeps IdP complexity in the layer you control (your app) and presents one clean interface to TS.

10 ABAC via RLS with formula variables

// three independent objects that meet at query time · 10.15.0.cl+

The current recommended ABAC mechanism. Three pieces, each independently designed, that resolve only when a query runs. None of the three needs to know about the others directly — that's the architectural point.

Object 01

Formula variable

A named, typed bucket. region_var of type VARCHAR. Created once at the cluster or Org. Doesn't know about any column or rule.

Object 02

RLS rule

Lives on a Table. Binds a column to a variable: region = ts_var(region_var). Authored by the data team, not the auth team.

Object 03

Variable values

Per-user assignment. Set in the token request or via a values-update API. region_var = ['NA','EMEA'] for this user.

// three independent objects, resolved at query time

The lifecycle, one step at a time

STEP 01 · AUTHOR ONCECreate the formula variable

Variables are independent objects with a name and a data type. The request-parameter reference lists VARCHAR, INT32, INT64, DOUBLE, DATE, DATE_TIME for formula-variable values; note that the Variables overview page also lists BOOLEAN and TIME (and BIGINT/INT/FLOAT spellings) as supported, so the two halves of TS's own doc disagree. Test before relying on BOOLEAN or TIME. DATE/DATE_TIME values are passed in epoch format.

POST /api/rest/2.0/template/variables/create
{
  "type": "FORMULA_VARIABLE",
  "name": "region_var",
  "is_sensitive": false,
  "data_type": "VARCHAR"
}

STEP 02 · PER TABLEAdd the RLS rule that references the variable

In the Row Security Editor on a Table, write the rule using ts_var(varName). No quotes around the variable name. The rule applies to every Model, Liveboard, and Answer derived from this Table.

RLS rule on orders table
// single variable
region = ts_var(region_var)

// multiple variables (AND)
region = ts_var(region_var) AND department = ts_var(department_var)

// group override: admins bypass, everyone else filtered
'admins' in ts_groups OR region = ts_var(region_var)
i
The "= becomes IN" rule
If the variable is assigned a single value, region = ts_var(region_var) generates WHERE region = 'NA'. If the variable holds multiple values, the same rule generates WHERE region IN ('NA','EMEA'). Same syntax, both behaviors. The engine inspects the variable's value count at query time.

STEP 03 · PER SESSIONAssign values via the token request

When your backend mints a token for the embedded user, include variable_values and a persist_option. Your token service is where tenant context, entitlements, and business logic decide what each user gets.

}

Persist options

!
The default is APPEND, not REPLACE — set it explicitly
The default persist_option on auth/token/custom is APPEND. A stateless token service that omits the field will accumulate entitlements across mints rather than overwrite them, which is the slow-leak failure this whole pattern is meant to prevent. For a stateless service, always send REPLACE.
ValueBehavior
REPLACEReplaces the user's persisted set with what's in this request. Omitting a value from the payload removes it. The right choice for a stateless token service — but you must set it, because it is not the default.
APPENDThe API default. Adds the values in this request to whatever the user already has persisted. Useful for deliberate incremental grants; dangerous when used by accident in a per-session mint.
NONEMint the token but do not persist its entitlements to the user object. Correct for pure cookieless where you re-mint every session and do not want scheduled reports running with stale persisted values.
RESETClears all persisted entitlements on the user object. This is the documented way to wipe a user's stored ABAC (for example, on offboarding or a tenant change). Current and supported — not legacy.

Persisted values are used for scheduled exports, alerts, and cookie-based sessions — anything that runs when no fresh token is provided. So persistence is about what happens between tokens. For pure cookieless with re-mint on every session you may want NONE; if you persist, use REPLACE so each mint is authoritative. If tenant context changes mid-session, re-mint with REPLACE (or RESET then re-mint).

Fail-closed by design: is_mandatory_token_filter and TS_WILDCARD_ALL

The "no rows visible when the variable is unset" behavior in the table above is not automatic across the board — it's something you opt into per column, and a security compendium should call out the actual mechanism. On any column in a Model, set is_mandatory_token_filter: true in the TML. ThoughtSpot then refuses to return data for that column unless the token (or the resolved RLS) supplies a value for it. A user with no entitlement on a mandatory-filter column sees nothing, rather than everything. That is what turns "the RLS rule happened to fail closed" into "I architected deny-by-default."

The escape hatch is the reserved wildcard. To deliberately grant a user all values on a protected column — an admin, a support role, an internal superuser — pass the keyword ["TS_WILDCARD_ALL"] as the value, either as the variable value in the token or in the RLS rule itself. This is the clean, auditable way to express "this principal sees everything," instead of leaving the column unprotected or maintaining a parallel set of bypass rules.

i
Why this pairing matters
Without is_mandatory_token_filter, a column is open by default and your security depends on every RLS rule being present and correct — one missing rule leaks the column. With it, the column is closed by default and you explicitly open it, per principal, via the variable value or TS_WILDCARD_ALL. Deny-by-default is the posture you want on anything sensitive; this is how you get it.

Variable scoping

Variables can be assigned at different levels. The token request handles the user level, which is what most embedded ABAC needs:

  • User level — dominant pattern. Set per user via the token request. Each user carries their own values.
  • Org level — same variable name, different default per Org. Useful in multi-tenant setups where the tenant default is the right answer 90% of the time.
  • Data model level — variables can parameterize TML, connection properties, and metadata objects, separate from data security.

In the token request you can also scope with org_identifier and objects to limit which Org or specific objects the variable assignment applies to.

Two production gotchas in the legacy pattern

⚠ filter_rules and parameter_values are linked

13 The full filtering stack — six layers, ordered

// only the top two are security · the other four are SDK or UI

TS has six distinct filter mechanisms that all generate WHERE clauses against the same underlying query. Teams regularly confuse them, and the most common (and dangerous) mistake is treating runtime filters as security. The order matters because higher layers cannot be overridden by lower ones — that's what makes RLS and ABAC trustworthy, and what makes runtime filters fundamentally not a security mechanism.

// six layers · the green band is security · the orange band is UX · all become WHERE clauses

The two that are security

L1
RLS Rules
Defined on the Table. Tied to the user's identity and group memberships. Multiple RLS rules on the same Table combine with OR (any matching rule grants visibility). Always applied; cannot be turned off by the user or by anything in the SDK. Covered in depth in §10.
L2
ABAC filter rules
Set via the token mint request (variable_values, or legacy filter_rules). Stamped onto the signed JWT, locked in for the session. Multiple clauses combine with AND. Cannot be overridden by anything downstream — including runtime filters set in the browser. Covered in §10–§11.
i
One axis this stack doesn't cover: column-level security
All six layers here are row filtering — they decide which rows a query returns. Column-level security (CLS) is a separate axis: it decides which columns a user can see at all, by granting or denying column access to groups (the CLS groups in the §15 taxonomy). It's enforced server-side like RLS, can't be bypassed from the SDK, and composes with everything above — a user can be filtered to NA rows by RLS and simultaneously denied the salary column by CLS. Pillar 4 ("which data?") is really two questions, rows and columns; this section answers rows.

The four that are not

Layer 3 — Runtime filters & Runtime Parameters. These are the most commonly misunderstood. They're set in the SDK at embed init time:

    { columnName: "Region",
      operator: RuntimeFilterOp.EQ,
      values: ["NA"] },
    { columnName: "Revenue",
      operator: RuntimeFilterOp.GT,
      values: ["100000"] }
  ]
});

Under the hood, these become URL query parameters (?col1=Region&op1=EQ&val1=NA). Operators include EQ, NE, IN, NOT_IN, LT, LE, GT, GE, CONTAINS, BEGINS_WITH, ENDS_WITH, BW, BW_INC. They can be updated after render via HostEvent.UpdateRuntimeFilters.

!
The most common dangerous mistake
"We'll just pass tenant_id in runtimeFilters." Wrong. Runtime filters become visible URL parameters. A user opens dev tools, edits val1=acme to val1=competitor, refreshes, and sees the competitor's data. Tenant isolation is RLS or ABAC, full stop. The same applies to per-user filtering (user_id = current_user) — that must be enforced server-side.

Layer 4 — Liveboard filters

The filter chips that render at the top of an embedded Liveboard. The Liveboard author sets default values when editing; once published, users can click any chip to open a modal dialog and change values. The dialog UI adapts to the column's data type (string list, date range, number range, etc.).

Three ways to use them in an embed:

  • Let TS render the default UI — chips appear at the top of the Liveboard, users click them, results refresh. No code on your side.
  • Hide TS's chips and build your own filter UI in your app. Set hideLiveboardHeader: true, then drive everything through host events.
  • Show TS's chips but programmatically read or update them — useful when your app needs to track filter state, sync URL state, or react to user filter changes.

Layer 5 — Liveboard cross filters

When a user clicks a value in a chart on a Liveboard (a bar, a pie slice, a row in a table), TS can apply that value as a temporary filter to all other visualizations on the same Liveboard. This is the brush-and-link pattern: click a region in one chart, watch every other chart on the board respond.

Cross filters interact with regular Liveboard filters on the same column:

  • If a Liveboard filter already exists on the clicked column, the cross filter replaces the values in that existing filter for the duration of the brush.
  • If no Liveboard filter exists on the column, a new temporary filter chip appears in the header showing the cross filter values.
  • When the user clears the cross filter (clicking the same element again, or dismissing it), the chip disappears and the original Liveboard filter values (if any) are restored.

Layer 6 — Search query filters

The lowest-precedence layer. These are filter conditions baked into an Answer's search_query string — the TML field that captures the natural-language search that produced the Answer. An Answer built from the search "revenue by region for 2026" has a search_query that includes [date] = 2026. That's a search query filter.

Where they show up vs where they don't:

  • Visible in SearchEmbed (when users explore an Answer directly), and in Liveboard Edit mode (when the author is editing a viz). The filter UI appears above the chart.
  • Not visible on the published Liveboard. The filter is applied silently to the viz's query.

Override behavior is the key thing to understand: when a viz with a search_query filter is on a Liveboard, any Liveboard filter (Layer 4) on the same column fully overrides the search_query filter for that column. The author's baked-in filter loses to the user's chip. So if an Answer has [region] = 'NA' baked in, and the Liveboard has a Region filter, the Liveboard filter wins — even if the Liveboard filter is set to all-regions.

Which layer should I use for what?

USE RLS / ABAC FOR

Anything where being wrong means a data leak

Tenant isolation. Per-user customer lists. Department-scoped data. Region restrictions tied to the user's role. Anything the user must not be able to bypass by editing a URL or the SDK call.

USE RUNTIME FILTERS FOR

Drill-down navigation from your app

"Show this Liveboard filtered to Customer X" because the user clicked Customer X in your own UI. The user could already see all customers — runtime filters are about narrowing the view for convenience, not about preventing access.

USE RUNTIME PARAMETERS FOR

What-if scenarios

"Show forecast at 15% profit margin vs 20%." Parameters drive formulas; runtime overrides let your app pass scenarios into the embed without writing them into the Liveboard.

USE LIVEBOARD FILTERS FOR

User-driven exploration

The user wants to slice and dice. They click a chip, change a value, results refresh. Default filters set in the Liveboard editor.

i
A useful mental test
For any filter you're considering, ask: "If a user edits the URL or replaces the SDK init code, can they see data they shouldn't?" If yes → it's the wrong layer. Move it up to RLS or ABAC. If no → it's fine where it is.

14 Individual users vs shared service account

// the second big architectural choice · the answer is almost always individual

Every embed needs to mint tokens as someone. The choice is: each end-user has their own TS user record (created on demand via auto_create) and tokens are minted as that user — or there's a single shared service account in TS and every end-user's tokens are minted as that service account. The first is right for almost everything. The second is a temptation that ships fragile architecture.

PATTERN · INDIVIDUAL USERS (recommended)

One TS user record per real human

Alice Reed signs into your app, your backend mints a token with username: "alice@vantagesales.com", auto_create: true. TS creates the user record on first use, reuses on every subsequent call. Alice's actions are attributed to Alice throughout TS.

ANTI-PATTERN · SERVICE ACCOUNT

One shared TS user for the whole tenant

Alice signs in, your backend mints a token with username: "svc_vantage_sales". So does every other user at Vantage Sales. TS has one user record for the whole tenant. Every action is attributed to svc_vantage_sales.

The four things that break with a shared service account

IndividualAudit shows the real userEach access logged with the actual end-user identity. Forensics, compliance, and incident response work as expected.

The three-question test

If the answer to ANY of these is yes — and it almost always is — individual users is the only viable architecture.

1
Will different end-users see different data? If region, customer assignments, role, or any other ABAC varies between users — individual. The race condition on a shared user record makes service account unsafe.
2
Do users run any async work (alerts, scheduled exports, pinned Liveboards)? If yes — individual. Async jobs need stable user context. A shared service account doesn't have one.
3
Will anyone ever ask "who did that?" Internal investigation, compliance audit, customer dispute — if yes, individual. Service account audit is fiction.
✓
Service account is acceptable only for…
Public, read-only, identical-for-everyone embeds. A marketing landing page with a public live dashboard. No personalization, no ABAC, no audit requirement, no async. Anything else: individual users.

The license cost objection

The usual temptation is per-user licensing cost. The answer is to solve the license cost in the contract, not in the architecture. Embed pricing models exist precisely for this — usage-based, capacity-based, viewer tiers — so raise it with your ThoughtSpot account team. Don't trade away audit, ABAC, async, and personalization to shave a line item.

✗
If you go with a service account anyway
Document the four trade-offs you're accepting, in writing, signed off by your security and compliance owners. And go in clear-eyed: when SOC2 finds the audit gap, you'll need to rip out the shared user and rebuild everything as individual users. The migration cost dwarfs the license savings.

15 The full onboarding options tree

// the decision tree for any new TS deployment, embed or standalone

The choices above are about embedded analytics specifically. Here's the broader picture — every TS deployment fits somewhere on this tree, and recommended paths are marked. Use it to plan a new deployment or to validate where an existing one landed.

i
How TS Orgs actually deliver the isolation this tree keeps recommending
Orgs are the multi-tenancy answer throughout this tree, so the mechanics worth knowing: an Org is a logical partition with its own users, groups, and content, so cross-tenant access is architecturally impossible rather than rule-dependent. In Trusted Auth you target one by passing org_identifier in the token request, so the same backend mints into the right tenant per user. Each Org can have its own OIDC/SAML config (per-Org OIDC), which is how you support customers who bring their own IdP — but that path requires Orgs enabled and is heavier to change than app-layer IdP routing. One operational gotcha that bites ABAC automation: the variables APIs (create/search/update-values/delete) can only be called from the primary Org, and a formula variable created on the primary Org is what's usable across all Orgs. Plan your variable provisioning to run against primary, not against a tenant Org.

Most of it lives in Develop > Customizations > Security settings (or via POST /api/rest/2.0/system/security-settings/configure); the rest is SDK init configuration.

Because they're mandatory setup, treat them as security controls, not plumbing: list only the exact domains you serve from.

!
Keep the allowlists tight
No wildcards broader than you need, and no localhost entries left over from development in a production cluster — a stale dev entry means any process on a developer machine can iframe production data. On instances with Orgs, CSP allowlists are cluster-level only (configure from the All Orgs context); the CORS allowlist can also be set per Org. Org-level settings take precedence over cluster-level within that Org.

2 · Block non-embed full app access

By default, a user provisioned through your embed could navigate to the ThoughtSpot instance URL directly and land in the full standalone application — a UI surface you didn't design, with navigation you don't control. Two switches close this off:

  • Block non-embed full app access — the admin toggle under Develop > Customizations > Security settings (available at cluster and per-Org level). Note it does not restrict users with administrator or developer privileges.
  • blockNonEmbedFullAppAccess in the SDK's init() (SDK 1.22 / 9.3.0.cl+, default true) — prevents embed users from reaching TS pages outside the iframe.

3 · Action surface — visibleActions, hiddenActions, disabledActions

Every embed component accepts three arrays that shape what users can do: visibleActions (an allowlist — only these appear; everything else is hidden), hiddenActions (remove specific actions), and disabledActions (gray out but keep visible, with an optional disabledActionReason tooltip). Use either visibleActions or hiddenActions — not both.

action controls — embed constructorallowlist beats blocklist for customer-facing embeds
const embed = new LiveboardEmbed("#tsEmbed", {
  liveboardId: "...",
  visibleActions: [Action.DrillDown, Action.AddFilter, Action.Explore],
  disabledActions: [Action.Download],
  disabledActionReason: "Contact your administrator to enable exports"
});
!
Action config is UX, not enforcement
These arrays are client-side SDK configuration — the same mental test from §13 applies: anything a user could change by editing the SDK init code is not a security control. Hiding Action.Download improves the UI; it does not make data non-exportable. The enforcement layer is privileges on role groups (Can Download, Can Share, Has Spotter — the C3.b groups in §15). Set the privilege for enforcement, then mirror it in the action config so users don't see buttons that will fail.

4 · Token hygiene in the browser

  • Keep the token in memory. The SDK's getAuthToken callback fetches a fresh token whenever one is needed — there is no reason to write TS tokens to localStorage, sessionStorage, or your own cookies, where they outlive the page and widen the theft surface.
  • Never log tokens. Not in browser console output, not in backend request logs, not in your SIEM events (§07 Job 6 logs the mint event, not the token).
  • Tie logout together. When the user signs out of your app, end the TS session too — call the SDK's logout and stop serving tokens from /api/ts-token for that session. Otherwise the embed session can briefly outlive the app session it was vouched by.
  • HTTPS everywhere. The Bearer token rides the Authorization header on every embed request; plain HTTP anywhere in the path exposes it.

17 Custom actions — getting data out, safely

// callback vs URL actions · every custom action is a data egress path · scope it like one

Custom actions add your own buttons and menu items to embedded Answers, Liveboard visualizations, and Spotter responses — "Send to CRM," "Download branded PDF," "Create ticket from this row." They matter in a security document for one reason: every custom action moves data the user can see to somewhere new. The good news first, then the two flavors and how to keep each one tight.

✓
RLS and ABAC still govern the data
A custom action operates on the Answer behind the visualization, and that Answer was produced under the user's own authenticated session — RLS rules, ABAC variables, and CLS all already applied. An action can only carry rows the user could already see on screen. Custom actions widen where data can go, never which data the user gets. The controls in this section are about destinations and audiences, not row filtering.

The two flavors

CALLBACK ACTIONS

Data flows to your host app as an event

Clicking the action emits EmbedEvent.CustomAction across the iframe boundary via postMessage. Your app matches the action id, uses the payload's answerService (or embed.getAnswerService(vizId)) to fetch the rows, and runs whatever logic you want — build a PDF, write back to a system of record, open a tailored view. Created in Develop > Customizations > Custom actions, or injected at render time via the SDK's customActions array.

URL ACTIONS

Data is POSTed to a target URL

Clicking the action sends the Answer or visualization data directly to a web page or API endpoint you configure — no host-app code in the path. Created in the ThoughtSpot UI only. Because the browser ships user-visible data to an external destination, the perimeter controls below are not optional.

// callback = an event into your code, data stays in your app · URL = data straight to an allowlisted endpoint

What a callback action looks like

SDK-injected callback action + handlerthe id is the contract between button and handler
const embed = new LiveboardEmbed("#tsEmbed", {
  liveboardId: "...",
  customActions: [{
    id: "download-invoice-pdf",
    name: "Download PDF",                     // label users see
    position: CustomActionsPosition.MENU,     // PRIMARY · MENU · CONTEXTMENU
    target: CustomActionTarget.VIZ            // LIVEBOARD · VIZ · ANSWER · SPOTTER
  }]
});

embed.on(EmbedEvent.CustomAction, async (payload) => {
  const id = payload?.id ?? payload?.data?.id;   // New vs Classic experience
  if (id !== "download-invoice-pdf") return;
  const svc = payload.answerService ?? await embed.getAnswerService(vizId);
  const { columns, data } = await svc.fetchData(0, 1000);  // runs on the USER's session — RLS applies
  buildAndDownloadPdf(columns, data);
});

Operational nuances that cost time (not security, just gotchas): Liveboard-level actions carry a sessionless answerService — mint one with embed.getAnswerService(vizId); fetchData is paginated and returns column-oriented data; and the action id lives at payload.id or payload.data.id depending on the experience version.

The four controls that keep actions tight

1
Scope who sees the actionSecurity
When creating an action, the Show advanced availability setting restricts it to one or more groups. Treat data-egress actions ("Send to CRM," "Export PDF") like privileges: assign them to the role groups that need them (§15 C3.b), not to everyone. Also mind global vs local: a global action appears in the More menu of every visualization by default; a local action appears nowhere until someone assigns it to a specific visualization or Model — and any user with edit access to that object can do the assigning.
2
Allowlist URL-action destinationsSecurity
A URL action (or webhook) can only reach domains on the CSP connect-src allowlist — Develop > Customizations > Security settings, or connect_src_urls via the security-settings/configure API. Same discipline as §16: exact domains, HTTPS endpoints you own or trust, no leftover dev entries. The receiving endpoint gets user-visible data, so hold it to the same standard as any integration: authenticated, logged, and reviewed.
3
Minimize the payload with placementBusiness logic
Placement is a data-minimization tool. An action on the context menu (right-click on a data point) sends a single row; a primary or More-menu action operates on the entire dataset behind the visualization. If the use case is "create a ticket from this row," put it on the context menu and the full table never leaves the chart. Note only one primary action is allowed per visualization page.
4
Treat the callback handler as a trust boundaryIntegration
Once EmbedEvent.CustomAction fires, the data is in your JavaScript — ThoughtSpot's controls no longer apply. Whatever the handler does next (POST to your backend, hand to a third-party SDK, write to storage) is governed by your app's security, so apply the §07 rules to it: send to your own authenticated endpoints, log the egress event to audit, and never route the payload through client-controlled destinations.
i
SDK-injected vs UI-created — who controls the button
UI-created actions live in ThoughtSpot, need developer/admin privilege to create, and support the group-availability scoping above. SDK-injected actions (customActions in the embed config) are defined entirely in your code at render time — which means their visibility is your app's responsibility: render them only for users whose role warrants it, and remember the §16 rule that client-side config is UX, not enforcement. The enforcement for what the action can actually fetch remains the user's session (RLS/ABAC) either way.

Lifecycle rules that prevent the classic bugs

  • Call init() once, on page load. Don't gate it behind an async auth check — the SDK handles auth via getAuthToken when it needs a token, and the iframe is not bound by your app's CORS constraints.
  • Always embed.destroy() before re-rendering into the same container. Orphaned iframes leak memory and double-fire event handlers.
  • Prefer host events over re-renders. Runtime filters, cross filters, and parameters can all be updated live via HostEvent (§19) — re-render only when the object itself changes.
  • Pin the SDK version in production (e.g. visual-embed-sdk@1.49.0), never latest — an unpinned CDN URL means every release ships to your users untested. See §22 for the self-hosting option.

19 Events & host interop

// EmbedEvent = embed → host · HostEvent = host → embed · the seam your product is built on

Everything interactive between your app and the embed flows through two channels: EmbedEvent (the embed tells your app something happened) and HostEvent (your app tells the embed to do something). The custom-action and filter events were covered in §13 and §17; here is the working set, plus the three interop patterns that come up in nearly every real embed.

// two channels across one seam · listen for what happened, trigger what should happen
EventDirectionWhat it's for
EmbedEvent.Init / AuthInit / Loadembed → hostLifecycle + timing instrumentation; know when auth completed and content painted.
EmbedEvent.LiveboardRenderedembed → hostThe reliable "content is visible" signal — drive spinners off this, not Load.
EmbedEvent.Errorembed → hostSurface embed failures into your own error UI and telemetry instead of a dead iframe.
EmbedEvent.Saveembed → hostFires when a user saves content. There is no server-side save webhook — this client event is how your app learns about it.
EmbedEvent.CustomActionembed → hostYour buttons (§17).
EmbedEvent.FilterChanged / ParameterChangedembed → hostTrack user-driven filter state (§13).
HostEvent.UpdateRuntimeFiltershost → embedChange runtime filters live — no re-render, no iframe reload.
HostEvent.UpdateFilters / GetFilters / UpdateCrossFilterhost → embedDrive and read Liveboard filter state (§13).

Pattern 1 · Live filters, not re-renders

When your app's own filter UI changes, trigger HostEvent.UpdateRuntimeFilters on the existing embed rather than destroying and re-creating it. The update is near-instant; a re-render reloads the whole iframe.

!
Field lesson: UpdateRuntimeFilters has replace semantics — merge before you fire
Each UpdateRuntimeFilters call replaces the embed's full runtime-filter set. If two parts of your app each fire the event with only their own filters (a filter bar and a separate "runtime filters" panel, say), they will silently clobber each other — the last caller wins and the other's filters vanish. Keep one merged source of truth for runtime-filter state and have every caller send the union.

Pattern 2 · Drill-down with filter carry-over

"Click a row in the overview board, land on a detail board scoped to that row" is a destroy-and-re-render pattern: a custom action (or context-menu action) captures the clicked attributes, your handler merges them with the parent board's active filters, and re-renders a LiveboardEmbed pointed at the detail board with the merged set as runtimeFilters. Show your own Back affordance that re-renders the parent. Two details make it feel native: merge the parent's current filters in (so the drill respects what the user had narrowed to), and clear the drill state on any normal navigation.

Pattern 3 · Capture saves client-side

If users can save or edit content in the embed and your app needs to know (refresh a content list, tag the new object, log it), listen for EmbedEvent.Save and react in the handler. Don't poll the metadata API waiting for new objects to appear.

20 Styling & theming

// customizations.style in init() · variables are stable, selector rules are not

The goal of embed styling is for ThoughtSpot to look like a native part of your product. The SDK's init() takes a customizations.style object with three tools, and they differ sharply in upgrade-safety:

customizations — SDK initcustomCSSUrl loads first · inline customCSS overrides it
init({
  // ...auth config
  customizations: {
    style: {
      customCSSUrl: "https://cdn.yourapp.com/ts-theme.css",  // hosted stylesheet
      customCSS: {
        variables: {                                        // ← the stable, supported surface
          "--ts-var-root-background": "#F7F5FF",
          "--ts-var-root-font-family": "Inter, sans-serif",
          "--ts-var-button--secondary-background": "#F0EBFF"
        },
        rules_UNSTABLE: {                                   // ← escape hatch, name says it all
          '[data-testid="select-dropdown-header"]': {
            "background-color": "#ABC7F9!important"
          }
        }
      }
    }
  }
});
  • variables — use these first. The --ts-var-* set is the supported theming surface: backgrounds, fonts, buttons, chart palettes. Variables survive ThoughtSpot upgrades.
  • customCSSUrl — a hosted stylesheet for variables, @font-face declarations, and shared rules across multiple apps. Inline customCSS loads after it and wins, which gives you a base-theme + per-app-override structure.
  • rules_UNSTABLE — treat as debt. Selector-based rules target ThoughtSpot's internal DOM, need !important, and can break on any release upgrade — the suffix is the vendor telling you the contract. Keep every rule inventoried and re-test them as part of your cluster-upgrade checklist.
// later layers override earlier ones · stay as low in the stack as your design allows

One export path, deliberately
If you build a custom export, hide the native Download (visibleActions, §16) so there's exactly one way data leaves the embed — one dialog to control, one code path to audit, one egress event to log. And remember the two security anchors: interactive exports run under the user's session so RLS/ABAC apply automatically, while scheduled exports run against the user's persisted values — which is exactly why persist_option matters (§10).
!
Field lesson: proxy REST calls with the caller's token, not an admin token
Browser-to-cluster REST calls from a different origin hit CORS, so teams route them through their backend. When you do, forward the calling user's bearer token upstream. The tempting shortcut — the proxy minting one privileged token and serving everyone's reads with it — recreates the shared-service-account problem from §14 on the API path: user-scoped security silently stops applying and every read runs as the privileged identity.

Pre-rendering: three strategies, one trade-off

Embed startup cost is real — SDK assets, auth, metadata, data. The SDK's pre-render support (preRenderId + embed.preRender()) lets you pay it early, on your landing page, so the analytics page feels instant. The trade-off is always the same: the more you pre-load, the more you waste if the user never opens analytics.

StrategyWhat loads earlyChoose when
Pre-render with liveboardIdAssets + auth + that Liveboard's dataMost users open analytics, and you know which board — fastest, most resource-hungry
Pre-render without liveboardIdAssets + bootstrap; data deferred until renderThe balanced default — app warm, nothing board-specific wasted
prefetch()A few static JS/CSS assetsRarely worth it — browsers already cache static assets well
// three timelines, one trade-off: earlier content vs wasted work
pre-render without the board · render on navigation
// on your landing page — warm the embed
const embed = new LiveboardEmbed({ preRenderId: "analytics" });
embed.preRender();

// when the user opens the analytics page — attach the board
new LiveboardEmbed({ preRenderId: "analytics", liveboardId }).render();

Fetch discipline

!
Field lesson: derive, don't re-fetch — the N+1 filter-values trap
A custom filter bar needs the distinct values of each filterable column. The naive build fetches the Liveboard's data once per column — N sequential full-dataset round-trips (and if the calls go through a trusted-auth proxy, N upstream calls too). The fix that took a filter bar from sluggish to instant: one data fetch per Liveboard, derive every column's distinct values from that single payload, cache it keyed by board id, and dedupe concurrent callers on one shared promise. The general rule: any time you're about to call a data API in a loop, ask what single call the loop could be derived from.

Operational habits

  • Pin and vendor the SDK. Pin the exact version; for supply-chain control, vendor the pinned SDK (and its lazy chunks) onto your own origin instead of trusting a CDN indefinitely. Upgrade deliberately, re-testing rules_UNSTABLE styles (§20) and event handlers.
  • Keep an event log while developing. Wiring every EmbedEvent into a visible log pane turns "the embed is blank" from a mystery into a readable timeline (auth failed? render errored? wrong object id?). Keep a debug flag for it in production builds.
  • Keep REST credentials in sync with the embed session. If your app also calls REST APIs with the user's bearer token, refresh that copy whenever autoLogin re-mints — a stale bearer produces confusing 401s minutes after the embed itself recovered.
  • Smoke-test the seams. The highest-value automated checks are on your own glue: the token endpoint's guards (§07), the export proxy, static-file exposure. They're cheap to write and they're where regressions actually land.
